# 架构选项：控制跑在 PC 上，还是跑在 MCU 上？

> 起因：既然达妙电机有 ROS 控制包，能不能**把全部控制放在本机（Linux PC）**，MCU 不要了？
> 结论：**可以，而且这是"最快到达实机"的路；但不该丢掉 MCU——两者共用同一份生成代码，是同一内核的两个部署点。**

---

## 1. 先回答"知识库有没有这个方案"

**有，而且是教程里明确讲的一章。** 对应关系：

| 你要的东西 | 教程章节 | 关键结论 |
|---|---|---|
| PC 侧 ros2_control 全栈 | **M12 ros2_control 与硬件驱动** | `read → Σupdate → write` 三段式；@1 kHz 桌面实测 read/write 各 50–200 µs、JTC update 10–50 µs、导纳 50–100 µs，合计 160–550 µs，余量 450–840 µs |
| 实时性怎么保证 | **M11 实时 C++ 工程** | PREEMPT_RT + SCHED_FIFO + mlockall；cyclictest 判据 空载 <30 µs / CPU+IO <50 µs / 全压力 <100 µs |
| 总线怎么选 | M12 §EtherCAT/CAN | EtherCAT 飞行帧每从站 +1 µs、DC jitter <1 µs；CAN 受带宽限制 |
| 规划/集成 | M14 MoveIt2+MTC、M15 Mini-Manip | 规划 → ros2_control → 真机的完整链路 |
| 力控/导纳 | F05 导纳控制与 ROS2 工程 | 导纳环 50–100 µs，可放进 1 kHz |
| 轨迹时序 | M10 时间参数化 | 上位机做 Ruckig/TOPP，下位机只回放 |

**而且达妙自己就是这么做的**（官方开源，不是社区玩具）：

| 项目 | 架构 | 许可 |
|---|---|---|
| [达妙官方 7 轴谐波机械臂](https://gitee.com/kit-miao/7-axis-harmonic-drive-robotic-arm) | ROS 2 Humble + `ros2_control` 硬件接口 + **SocketCAN/CANFD（仲裁 1 Mbps / 数据 5 Mbps）** + **PC 侧重力补偿** + 拖拽示教 + MoveIt2 + Web 面板；8 台电机挂同一条 CAN 总线（ID 1–8，反馈 0x11–0x18） | BSD-3 |
| [Yerik15/damiao_ros2](https://github.com/Yerik15/damiao_ros2) | `ros2_control` SystemInterface，USB-to-CAN 适配器（`/dev/ttyACMx`），支持 **MIT 模式**（`position_des`/`velocity_des`/`kp`/`kd`/`feedforward`） | Apache-2.0 |

也就是说：**"本机跑全部控制"这件事，官方已经给了完整参考实现，连重力补偿都在 PC 侧。**

## 2. 三个方案的真实差异

| 维度 | A. 全 MCU（当前方案） | B. 全 PC（你提的方案） | C. 混合（推荐终态） |
|---|---|---|---|
| 控制频率 | 1 kHz 固定 | 500–1000 Hz（ros2_control） | PC 100–500 Hz → MCU 1 kHz 内环 |
| 周期抖动 | < 1 µs（确定性，WCET 可静态分析） | PREEMPT_RT 下 p99 **30–100 µs**；非 RT **200–1000 µs** | PC 侧抖动被 MCU 的内环与插补吸收 |
| 0.1 mm 可行性 | 任何速度 | **< 100 mm/s 稳过**；300 mm/s 时 200 µs 抖动 ≈ 60 µm，逼近极限 | 任何速度 |
| 安全 | 本地看门狗 + 力矩限幅 + 急停 | PC 崩了靠电机 MIT 模式的 Kp 保持；急停必须硬件 | MCU 兜底 + 硬件急停 |
| 开发速度 | 慢（改算法 = 重新生成 + 交叉编译 + 烧录） | **快**（C++/Python 直接改，Pinocchio 运行时可用） | 前期 B 快，后期 A 稳 |
| 生态 | 要自己写驱动 | **MoveIt2 / ros2_control / 官方包直接接** | 全都要 |
| 学习覆盖（教程） | M01/M03/M06/M11（部分） | **M12/M14/M15/F05/M10**（最完整） | 全覆盖 |
| 开源价值 | 高（代码生成是空白） | 低（已有官方实现） | **最高**（一份代码两端跑，没人做过） |

**关键的物理约束：总线带宽**

- 经典 CAN 1 Mbps，8 字节帧约 120–135 bit（含填充）→ 理论上限 **~7000–8000 帧/s**
- 6 轴 × 1 kHz × （命令 + 反馈）= **12000 帧/s** → **经典 CAN 装不下**
- 所以官方 7 轴臂直接上 **CANFD（1 Mbps 仲裁 + 5 Mbps 数据）**，8 电机共一条总线

这一条决定了：如果你走"全 PC"，**必须有 USB-to-CANFD 适配器**（官方清单里的那个模块），普通 USB-CAN（经典 CAN）跑 6 轴 1 kHz 会丢帧。

## 3. 我的建议：不是二选一，而是同一个内核换部署点

我们生成的本来就是**纯 C99、零依赖**的代码。这意味着**同一份 `arm_fk.h` 可以在三个地方编译**：

```
                    ┌──────────────────────────────┐
                    │  generated/arm_*.h（纯 C99）  │
                    └───────┬──────────┬───────────┘
                            │          │
              ┌─────────────▼──┐   ┌───▼──────────────┐
              │ x86 .so        │   │ ARM 固件         │
              │ （PC ros2_control│  │ （MCU 1 kHz 内环）│
              │   插件里直接调） │  │                  │
              └────────────────┘   └──────────────────┘
```

所以路线应该是**先 B 后 C，A 作为 C 的内环**：

| 阶段 | 做什么 | 产出 | 工期 |
|---|---|---|---|
| **P1：全 PC 跑通** | 用达妙官方 7 轴包改造出 6 轴：URDF + `ros2_control` 硬件接口 + CANFD + MoveIt2；重力补偿先用 Pinocchio 运行时 | 机械臂能动、能拖拽示教 | 1–2 周 |
| **P2：把 PC 侧算法换成生成代码** | `armgen` 生成 FK/雅可比/重力，编成 `.so`，塞进 hardware interface 替换 Pinocchio 调用；用双跑对比验证 0.1 mm | 同一份生成代码在 x86 上验证通过 | 1–2 周 |
| **P3：下沉到 MCU** | 同一份 `.h` 交叉编译进 H723，做 1 kHz 内环 + 限幅 + 看门狗 + 插补；PC 只发高层目标 | 混合架构，确定性 + 生态 | 2–3 周 |
| **P4：对比与发布** | 同一轨迹在 A/B/C 三种部署下测抖动、误差、丢帧；写成开源项目的 benchmark | 文章 + 数据 + 仓库 | 1 周 |

**为什么这个顺序最优**

1. **P1 让你最快摸到真机**，而且学的是教程里最完整的一章（M12/M14/M15）——比闷头做 MCU 三个月才看到机器人动，反馈快得多。
2. **P2 是关键的"验证杠杆"**：不用 MCU 就能验证生成器对不对（x86 上跑 1e6 组对拍），而且这份代码就是 P3 要用的**同一份**。出问题能立刻二分：是生成器的错，还是 MCU 部署的错？
3. **P3 才有独特性**：全 PC 方案官方已有、社区已有一堆，做出来只是"又一个 ros2_control 机械臂"。而"**同一份生成代码，从 PC 到 MCU 无缝下沉**"是没人做过的——这才是能发出去、能被引用的东西。
4. **P4 的对比数据本身就是内容**：MCU 确定性 vs PC 抖动的实测曲线，是最好的 README 首图。

## 4. 选择建议（按你的实际情况）

| 你的情况 | 建议 |
|---|---|
| 想在 2 周内看到机械臂动起来 | **走 P1（全 PC）**，MCU 先放着 |
| 想把这个做成毕业设计/论文 | **走 P1→P2→P3**，P4 的对比就是论文的实验章节 |
| 想发一个有影响力的开源项目 | **必须是 P2→P3**（一份代码两端跑），P1 只是前置 |
| 想做产品/长期维护 | **终态 C（混合）**，PC 规划 + MCU 伺服 + 硬件急停 |

**我的推荐**：**先 P1 打通实机（1–2 周），再回到 P2 用生成代码替换 PC 侧算法**。这样学习路径（M12/M14/M15）和开源价值（M06 代码生成）都不丢，而且顺序上先拿到"能动"的正反馈。

## 6. 方案 D：PC 做规划 + MCU 只做电机驱动（你的提案）

> 你的原话："MCU 端只跑电机控制驱动，PC 端负责所有规划，下发力矩给 MCU。"
> **方向完全正确——这就是业界标准的"上层智能 + 下层伺服"分层。但接口不该是"只发力矩"，应该是 MIT 设定点。**

### 6.1 为什么"只发力矩"是个陷阱

力矩接口的问题不在实现难度，而在**故障时的行为**：

| 故障 | 只发力矩（Kp=Kd=0） | 发 MIT 设定点（带 Kp/Kd） |
|---|---|---|
| PC 卡顿 50 ms | 力矩冻结 50 拍，机械臂在重力下加速 → 过冲/抖振 | 电机按最后设定点保持位姿 |
| 链路丢包 | 电机继续施加**陈旧力矩**，方向可能已经反了 | 位置保持，误差被 Kp 吃掉 |
| PC 崩溃 | 要么力矩冻结、要么归零 → **直接坠落** | 保持位姿（Kp 撑住） |
| 电机堵转/过流 | 只能靠驱动器自身保护 | MCU 可主动降 Kp、切零力矩 |

还有一个更硬的理由——**0.1 mm 的误差预算**：

> 力矩是"盲"命令，它只对被计算时的那一瞬间的 (q, q̇) 成立。
> 机械臂以 100 mm/s 运动时，链路延迟 1 ms 就意味着 **0.1 mm 的时序错位** ——
> 这一个人就把你的精度预算吃光了。而设定点接口有本地闭环，Kp 会吃掉这部分滞后。

**所以：把力矩当成"前馈项"（`tau_ff`）塞进 MIT 帧，而不是当唯一的命令。**

### 6.2 推荐的接口与分工

```
┌─────────────── PC (200–500 Hz) ───────────────┐
│ 规划 / IK / 轨迹 / 导纳 / 状态机 / 可视化     │
└───────────────┬───────────────────────────────┘
                │ 设定点：q_des[N], dq_des[N], Kp[N], Kd[N], tau_ff[N], seq, t
                ▼  （USB CDC / 以太网 / CAN，200–500 Hz，允许丢包）
┌─────────────── MCU (1 kHz，确定性) ───────────┐
│ ① 插补（把 500 Hz 设定点平滑到 1 kHz）        │
│ ② 重力补偿 g(q)（← 我们生成的代码，4.9 KB）    │
│ ③ 限幅：力矩、速度、位置、跟随误差              │
│ ④ 打包 MIT 帧 → CANFD → 6 台电机              │
│ ⑤ 看门狗：50 ms 没新设定点 → 减速/保持          │
│ ⑥ 故障处理：过流/超差/急停 → 零力矩             │
└───────────────┬───────────────────────────────┘
                │ 反馈：q, dq, tau, 状态, 时间戳（1 kHz）
                ▲
                └──────────── PC 用于状态估计与日志
```

**为什么重力补偿必须放 MCU**：它是安全相关的。PC 崩了之后，如果重力补偿跟着消失，机械臂会缓慢下垂（MIT 模式下不会坠落，但会塌）。`g(q)` 在 MCU 上只要 4.9 KB 代码、几微秒，**换来"PC 死了机械臂还能自己撑住"**——这是整个分层最值钱的一条。

### 6.3 六个角色，别越界

| 角色 | 放哪 | 理由 |
|---|---|---|
| 轨迹生成 / 时间参数化 | PC | 需要 Ruckig/TOPP，算力大，可预览 |
| IK | PC | 需要迭代、需要碰撞检查 |
| 导纳/阻抗外环 | PC（1 kHz 时也可放 MCU） | 需要力传感器数据，逻辑复杂 |
| **重力补偿** | **MCU** | 安全相关，PC 挂了也要工作 |
| **插补 + 限幅 + 看门狗** | **MCU** | 这才是"确定性"的全部意义 |
| **MIT 帧打包 → CANFD** | **MCU** | 时序要求最紧，抖动必须 < 50 µs |

### 6.4 链路延迟：USB CDC 有个必踩的坑

- USB FS（12 Mbps）本身够用（500 Hz × 60 B ≈ 30 KB/s）
- **但 Linux 的 `cdc_acm` 默认 `latency_timer = 16 ms`！** 不改它，你的"1 kHz 控制"实际是"62 Hz 的设定点更新"。
- 必须执行：`echo 1 | sudo tee /sys/bus/usb-serial/devices/ttyACM0/latency_timer`
- 这一条属于系统配置，**我会先问你**。或者把 MCU 侧的 USB 描述符改成小包 + `SOF` 同步。

实际端到端延迟（含插补）预计 **1–2 ms**，对 200–500 Hz 的设定点流完全够——因为**它不在快环里**了。

### 6.5 这套架构对我们代码的意义

| 我们生成的模块 | 在新架构里的位置 |
|---|---|
| `arm_fk` / `arm_jacobian` | PC 侧 IK 用（编成 `.so`）；也可给 MCU 做末端状态上报 |
| `arm_gravity` | **MCU 侧 1 kHz 跑**（安全相关，PC 挂了也工作） |
| `arm_rnea` | MCU 侧可选的力矩前馈（需要 dq/ddq，通常 PC 算） |
| `arm_aba` | PC 侧仿真/预测，MCU 不用（39.7 KB 可以省掉） |
| `arm_dls_ik` | PC 侧（100–500 Hz），不需要上 MCU |

**结论**：这套架构下，MCU 只需要 `gravity`（4.9 KB）+ 插补 + 限幅 + MIT 打包，**总代码 < 10 KB**，Flash 占用从 100 KB 降到 ~15 KB。而 IK/规划留在 PC，用 ROS2 生态。

**这反而让开源项目更清晰**：生成器不绑定"跑在哪个端"，用户按需选模块（`--enable gravity,fk`）。同一份代码，PC 用 `.so`、MCU 用 `.a`，这正是我们的差异化。
